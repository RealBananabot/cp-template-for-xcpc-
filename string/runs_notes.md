# Runs 模板：哈希与 SA 的 LCP/LCS 替换

所有模板依赖公共缺省源 [`../s.cpp`](../s.cpp)，使用 GNU C++20、`-O2`。当前代码按 ASCII（0～127）处理，统一使用 `size(s)` 和函数式数值转换，并通过 `-Wall -Wextra -Wconversion -Werror`。现场使用优先选择下面两份直接函数，减少需要手写的封装与外部依赖。

## 现场直接使用

- 哈希版：缺省源后粘贴 `runs_hash.cpp`，不依赖查询类或 `runs.cpp`。
- SA 版：缺省源、`sa.cpp` 后粘贴 `runs_sa.cpp`，不依赖查询类或 `runs.cpp`。

两份是同一接口的替代实现，选择一份即可：

```cpp
auto ans = get_runs(s);
```

返回约定相同：排序、去重的 `{l,r,p}`，0 下标闭区间，`p` 为最小周期。哈希版仍保留已复现的固定参数碰撞风险；SA 版使用精确查询。两份均支持空串和单字符输入，返回空数组。

查询和预处理均直接写在函数内部，使用局部 lambda；保留字符短路、32 位索引、64 位乘法和连续重复候选过滤。调整为 ASCII 约定前，曾通过 116700 组小数据与旧版、暴力结果的对照，地址及未定义行为检查，以及百万长度的重复串和 Fibonacci 串结果比较。碰撞回归用例中，直接哈希版与旧哈希版一致地失败，直接 SA 版与暴力结果一致。

独立哈希查询封装已移除，现场直接哈希 Runs 保留。下文提供 SA 查询封装的接口，并保留历史性能数据；性能表不是对这两份直接函数的重新测量。文中 116700 组输入、6448259 对查询是改为 ASCII 约定前的历史验证记录，含完整字节范围；当前 ASCII 版重新通过 67420 组 Runs 对拍、6251523 对查询检查，汇总见 [README.md](README.md)。

## 调用与依赖（SA 封装版）

确定性的 SA 版依次粘贴 `sa.cpp`、`lcp_sa.cpp`、`runs.cpp`：

```cpp
auto ans = get_runs<sa_lcp>(s);
```

也可以独立使用查询，或复用已经构造好的查询对象：

```cpp
sa_lcp t(s);
int ri = t.lcp(x, y);
int le = t.lcs(x, y);
bool less = t.cmp(x, y);
auto ans = get_runs(s, t);
```

- `lcp(x,y)`：从 `x`、`y` 开始向右的最长公共前缀长度。
- `lcs(x,y)`：分别以 `x`、`y` 结尾的最长公共后缀长度，包含位置 `x`、`y`。
- `cmp(x,y)`：后缀 `s[x..]` 是否严格小于后缀 `s[y..]`。
- 查询下标均在 `[0,n)`；空串可以构造，但不存在合法查询下标。`get_runs(空串)` 返回空数组。
- `get_runs` 返回排序、去重后的 `vector<tuple<int,int,int>>`，三元组为 `{l,r,p}`：0 下标闭区间 `[l,r]`，`p` 为最小周期。向 P6656 输出时，只给 `l`、`r` 加一。
- `sa_lcp` 不保留原串引用。传入 `get_runs(s,t)` 的查询对象必须由同一字符串构造。
- 按 ASCII（0～127）比较，不做 Unicode 码点解码。哈希版要求 `n < INT_MAX`，SA 版要求长度能用 `int` 表示，且内存足够；均不在热路径检查下标。

## 正确性审查

原枚举主体在使用精确 LCP/LCS 与后缀顺序时，暴力检查未发现错误。栈中剩余位置始终大于当前扫描位置，因此删除了原 `chk` 中不必要的交换。

原版不能处理空串，直接访问 `pw[0]`、`pre[0]`；模板版已补充支持。这是模板的适用范围扩展，P6656 的输入本来是非空串。

固定参数 `base=107897, mod=998244353` 存在实际碰撞：

```text
hash("atdeoqmh") = hash("atofnybk") = 589312048
```

下面这个符合题目字符范围的 32 字符输入会使用户提供的原代码和本次整理的哈希版多报一个 run：

```text
atdeoqmhatdeoqmhatofnybkaaaaaaaa
```

正确的 0 下标结果：

```text
(0,17,8)
(24,31,1)
```

哈希版还会返回 `(0,24,8)`。该区间并不以 8 为周期，因为 `s[18]='o'`，而 `s[10]='d'`。正确结果已由暴力最小周期枚举独立确认，SA 版与之相同。

单固定哈希的二分判等没有确定性保证；碰撞还可能破坏二分所依赖的单调性。哈希版保留用于速度和空间比较，并在代码头注明限制。

## 实现与复杂度

| 部分 | 单固定哈希 | SA + 两份稀疏表 |
|---|---|---|
| 查询预处理时间 | O(n) | O(n log n) |
| 查询结构空间 | O(n) | O(n log n) |
| 单次 LCP / LCS | O(log n) | O(1) |
| 单次后缀比较 | O(log n)，首字符不同可直接返回 | O(1)，直接比较 rk |
| 含排序的 runs 总时间 | O(n log n) | O(n log n) |
| 正确性 | 存在已复现的碰撞反例 | 确定性 |

SA 版分别为正串、反串建立 SA 与 height，并对 height 建区间最小值稀疏表。反串排名用于求 LCS，正串排名直接用于后缀比较。两份稀疏表在 `n=1000000` 时合计约 144.6 MiB，另有约 7.6 MiB 的正反排名数组，以及构造、枚举和输出所需空间；这份实现不适合 128 MiB 的内存限制。

保留的小幅优化：索引和哈希数组使用 `int`，乘法显式转 `i64`；前缀哈希使用 `n+1` 个元素和左闭右开区间，省去特判；LCP/LCS 首末字符不同直接返回 0；连续生成的相同 run 提前过滤，最终仍统一排序去重。最坏复杂度不变。

## 性能测试（历史封装版）

测试日期：2026-11-04。CPU：AMD Ryzen 7 H 260。编译器：GCC 15.2.0，`g++ -std=gnu++20 -O2`。比较的是本次整理并优化后的哈希版与 SA 版，共用同一个 runs 枚举主体。

每组分别在独立进程运行三次，交替执行两版；耗时取中位数，RSS 取三次最大值。总耗时包含查询结构构建、候选枚举、排序及去重，不含输入输出、结果校验和对象销毁。内存为 `/usr/bin/time` 测得的完整进程峰值 RSS，包含输入串、查询结构、栈和结果。三次各列分别取中位数，因此预处理与枚举两列相加可能与总耗时略有差异。

随机串使用 Python `random.Random(6656)`，按长度 200000、1000000 的顺序分别先生成 26 字母随机串，再生成二进制随机串。周期串是 `abacaba` 重复后截取前 n 字符；Fibonacci 串从 `a, ab` 开始按 `a,b = b,b+a` 延长后截取；Thue–Morse 串第 i 个字符为 `"ab"[popcount(i) mod 2]`。

12 组基准输入的两版结果均进行了完整的三元组序列比较；结果一致。上面的独立碰撞反例不在这些基准输入内。

## 补充：相对用户原版哈希的效率

重新在同一轮中比较三种实现，长度均为 1000000。原版保留用户代码的 64 位索引、哈希数组、栈、三元组，以及原始二分查询和最终排序去重；循环变量也按原 `#define int long long` 使用 64 位整数。仅省略不参与计时的主程序和调试代码。

编译环境、输入数据与前面的基准相同。各版本在独立进程中运行三次，每轮轮换执行顺序，耗时取中位数，RSS 取三次最大值。这次对整个 `get_runs` 函数调用计时，包含函数内部局部对象的销毁，排除输入输出、结果校验及返回数组的销毁。三者计时范围一致；与前面拆分预处理的计时方式略有差别，数据也存在轮次波动，应在本表内比较。

| 数据 | 原版哈希 / ms | 优化后哈希 / ms | SA / ms | 哈希提速（原版/优化后） | SA 提速（原版/SA） |
|---|---:|---:|---:|---:|---:|
| 26 字母随机串 | 328.4 | 81.5 | 223.9 | 4.03 倍 | 1.47 倍 |
| 二进制随机串 | 541.1 | 394.5 | 288.9 | 1.37 倍 | 1.87 倍 |
| 全部相同字符 | 317.7 | 246.7 | 192.5 | 1.29 倍 | 1.65 倍 |
| 周期串 abacaba | 421.8 | 236.4 | 216.0 | 1.78 倍 | 1.95 倍 |
| Fibonacci 串 | 493.4 | 333.8 | 347.5 | 1.48 倍 | 1.42 倍 |
| Thue–Morse 串 | 505.7 | 367.2 | 720.6 | 1.38 倍 | 0.70 倍 |

提速比小于 1 表示更慢：本轮 Thue–Morse 串上，SA 耗时约为原版哈希的 1.42 倍。优化后哈希在这六组数据中约快 1.29–4.03 倍；SA 相对原版在其余五组数据中约快 1.42–1.95 倍。

优化后哈希在本轮的峰值 RSS 比原版下降约 39%–67%。主要改动是首末字符不同直接返回 0、使用 32 位索引和存储并在乘法处显式转 64 位、过滤连续重复的候选 run。26 字母随机串上，短路判定省去了大量二分；全相同字符的查询仍需二分，时间收益相对有限，但重复候选的过滤降低了内存和排序开销。未做逐项消融测试，未将总收益按单项优化量化分摊。
